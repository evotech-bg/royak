## Current code-supported boundary

- `workload::plan_pod` maps PVCs and StatefulSet claim templates to local host
  paths and marks the plan `host_local`. It does not replicate volume bytes.
- `reconcile_docker::choose_node` chooses `ctx.me` for `host_local`. That is the
  current scheduler's node, not a durable volume-owner identity.
- `StoredPV` records a path/class/access-mode/status/claim, but no durable node
  binding, attachment epoch or storage backend volume identity.
- PVC auto-binding now compares positive integral byte capacity and checks the
  reciprocal binding before workload planning. RWO/RWX metadata is not evidence of enforced node-attachment
  and fencing semantics. RWO alone is not Kubernetes single-pod-writer semantics.
- The existing StatefulSet smoke demonstrates same-node ordinal/data reuse.
  The external-ledger soak demonstrates acknowledged application writes in that
  ledger. Neither proves data-volume recovery after the original node is lost.

**Blocking risk, supported by code inspection but not yet a dedicated runtime
reproducer:** after scheduler/node change, the same logical PVC/path can resolve
to a different machine's local directory. Existing `host_local` routing is not
a distributed-volume ownership guarantee. Do not claim stateful failover, RPO=0
or safety against dual writers from it.

replicated block backend, while Royak owns namespace/claim identity, scheduling,
authorization and safe attach/detach lifecycle. A candidate is LINSTOR/DRBD:
the official [DRBD project](https://github.com/LINBIT/drbd) describes replicated
block devices with quorum, and the [LINSTOR guide](https://linbit.com/drbd-user-guide/linstor-guide-1_0-en/)
documents volume management and backups. This is a candidate, **not a selected
dependency or an ARM64/Ubuntu-kernel/package/license validation**. Kubernetes
integration is not the intended Royak integration path.

The initial evaluation will use LVM2 for disk allocation and DRBD 9 for the
replication data path, with a versioned Royak storage-driver boundary. Compare
a constrained native management agent against LINSTOR-backed management for
correctness, failure recovery, ARM64/kernel compatibility, distribution terms
and actual resource use. Do not infer that native management is automatically
smaller or safer. Storage is optional Linux functionality, not an undocumented
dependency imposed on every Royak installation. No new replication protocol or
chunk format is approved as a production shortcut.

Alternative: design a Royak-owned replication engine. That is a separate
storage/data-consistency project, not a small extension to Service routing or
Raft metadata replication. In particular, copying directories after a pod
restart does not establish synchronous durability, fencing or crash consistency.
This alternative is not the currently approved first implementation direction.

Initial proposed contract: one filesystem volume, RWO/single-node attachment
and an additional beta restriction to one active writer pod, explicit
volume/node/attachment identity, three replicas with synchronous durability
rules and a fenced handoff. No RWX/shared-filesystem or arbitrary storage API
claim. The selected backend must be evaluated for its actual quorum/flush/FUA,
failure and recovery semantics before this contract is finalized.

## Backup engine — foundations integrated, full scope NOT QUALIFIED

The active native foundation now includes namespace/claim/volume-bound durable
job state, separate capture/repository-check/restore evidence, file/Raft commit
validation, disk schema6 and a separate backup AEAD domain. Before later runtime
changes, the actual root suite passes360/360 with no ignored tests, including
real restic capture/full-data-check/new scratch restore and corruption/revocation
negatives. This is not a live volume or PostgreSQL result. Live immutable source
and fresh-volume restore capabilities remain unconstructible/unavailable;
HTTP scheduling, cross-node/cgroup descendant recovery, recovery escrow,
off-host repositories, schedules/retention and full recovery are still required.
Repository-check evidence rollback/invalid-ack findings are being corrected;
new source requires a complete exact-build join. Mandatory real-adapter tests
must receive a signature-verified pinned native/Linux restic; absence fails,
never silently skips. CI tool setup and Linux execution are not yet accepted.

Use **restic as the first backup-engine candidate**, behind a replaceable
adapter. Royak owns authorization, policy, scheduling, source consistency,
job status, restore plans and evidence; restic owns its repository format,
chunking/deduplication, encryption and data transfer. Pin the tested executable
version and hashes for Linux ARM64/native test tools before execution. A
successful third-party command is not sufficient Royak restore qualification.
References: [restic backup/exit semantics](https://restic.readthedocs.io/en/stable/040_backup.html),
[repository integrity checks](https://restic.readthedocs.io/en/stable/045_working_with_repos.html),
[restore behavior](https://restic.readthedocs.io/en/stable/050_restore.html), and
[repository/key handling](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html).

### Three different guarantees

- **Replication** maintains available copies of the current dataset; replicated
  deletion/corruption is not historical recovery.
- **Storage snapshots** anchor a point-in-time dataset, with an explicitly
  declared consistency level. A snapshot retained on the same storage is not
  an independent backup.
- **Backups** retain encrypted historical recovery points in an independently
  configured repository. A local repository suffices for owned test fixtures,
  not physical-host disaster recovery. An off-host destination and recovery
  keys require separate explicit provisioning; no cloud bucket/account is
  created automatically by this scope approval.

### Source and metadata contract

1. A job resolves a namespace UID, claim UID, backend volume identity and exact
   storage-snapshot/export identity. It does not accept arbitrary host paths,
   cross-namespace names or workload-supplied shell commands. A recreated claim
   with the same name cannot adopt the former claim's data or backup authority.
2. The first generic volume path is a **cold/quiesced or read-only immutable
   source** with proven absence of active writers. Refuse unsafe live-directory
   backup rather than silently downgrading consistency. Later crash-consistent
   snapshots and application-consistent adapters must be separately labelled
   and qualified. PostgreSQL needs a clean stopped source, an appropriate
   consistent storage snapshot including required WAL, or an explicitly tested
   database backup adapter; restic copying a live data directory alone does not
   establish a valid database backup. See the official
   [PostgreSQL filesystem-backup requirements](https://www.postgresql.org/docs/current/backup-file.html).
   Multi-volume atomic consistency and generic point-in-time DB recovery are
   deferred, not implied by chunking.
3. Store a versioned recovery manifest inside the protected backup: source and
   destination identities, namespace/volume UIDs, driver/format versions,
   consistency level, capture bounds, exact repository/snapshot ID and relevant
   desired-state generation. Hashes bind approval and evidence; a plain hash is
   not a replacement for authenticated storage or authorization.
4. Separate **control-plane export** from volume data. Existing `royak backup`
   serializes `load_state(state_path)` and is not a volume backup. The inspected
   `persist::load` path does not read the authoritative clustered Raft directory
   and may synthesize fresh state for a missing file; this is a code-supported
   risk, not a new runtime reproduction. A new live-cluster export must read an
   authorized consistent committed state and record its boundary, or refuse.
   Do not use a possibly stale seed file or copy a mutating Raft directory as
   proof of recoverable cluster state. Existing backup/restore commands are not
   silently repurposed by this document.
5. Define which Secrets are exportable under separate explicit permission and
   which recovery keys must be escrowed outside the failed cluster/repository.
   Do not restore old Connect sessions, attachment grants or Raft peer identities
   as live authority. Rebinding restored metadata to restored data is explicit;
   workloads remain blocked until validated data volumes are attached.

### Execution, security and status contract

- Namespace-scoped backup authority is data-export authority, not ordinary
  read/view permission. Restore, Secret export, repository administration and
  destructive retention operations have separate authorization. Tags or
  snapshot filters alone are not tenant isolation; repository credentials and
  backend boundaries must enforce the declared scope.
- Use approved destinations only, verified TLS, protected password/credential
  references, redacted output and a restricted child environment. Never place
  secrets in process arguments, logs or evidence bundles. No credential search,
  insecure TLS fallback, arbitrary shell hook, model-authorized export or
  automatic initialization of an unknown repository.
- Use bounded background jobs, concurrency/bandwidth/cache limits and explicit
  cancellation. No backup process or synchronous filesystem/network wait on an
  async API worker. Prevent overlapping conflicting jobs per repository/volume;
  record partial remote effects after failure and reconcile before retries.
- Distinguish **Captured**, **RepositoryChecked** and **RestoreVerified**.
  A restic backup exit 3 is an incomplete snapshot, not Captured/Succeeded.
  A metadata-only `restic check` is not full data verification; declared full
  verification uses `check --read-data` within an explicit bandwidth budget.
  RestoreVerified additionally requires an isolated restore and byte/application
  validation. Each status records exact evidence and its freshness, not a
  permanent boolean that all future restores are safe.
- Repository passwords/recovery keys must remain recoverable independently of
  the lost cluster. Loss of those keys is not repaired by having more replicas.
  Encryption and scoped credentials do not themselves prove immutability or
  ransomware resistance; those require tested repository-side protections.
- Retention is opt-in policy with a preview, protected last known verified
  recovery point, separate destructive authority and serialized pruning.
  No automatic `forget`, `prune`, unlock or cleanup of an unfamiliar repository.

### Restore-first safety and acceptance

Restore into a **new owned volume/directory** by default, using an exact full
snapshot ID and an approval bound to namespace, destination, manifest and
current plan hash. Never restore over a running volume or use restic's default
overwrite behavior implicitly. In-place recovery is out of the first version.
Resume applications only after integrity checks and an explicitly authorized
cutover; retain the source volume/backup for diagnosis.

Before claiming this engine implemented/qualified, require real isolated tests:

1. Cold data backup, full data check, restore to a fresh target and exact file
   bytes/metadata comparison; repeat after source deletion.
2. Real PostgreSQL backup/restore with the declared consistency method, fresh
   database startup and independent transaction/content checks.
3. Interrupted upload/restore, process death, full disk, unavailable repository,
   wrong key, missing/corrupt chunks and incomplete source/exit 3. No false
   Captured/RestoreVerified status or overwrite of an existing target.
4. Namespace/claim recreation, path/symlink escape, tampered manifest, stale
   approval, unauthorized Secret export and permission withdrawal. Audit only
   metadata, with no credentials or unrelated data in logs.
5. Repeated incremental backups and retention previews, verified recovery after
   an authorized prune, concurrency/cancel/restart reconciliation, bounded
   clients/sockets/processes/cache and cleanup of exact owned resources only.
6. Control-state recovery coordinated with restored data, missing-authoritative-
   state rejection, independent recovery keys and no resurrection of sessions
   or old writer authority. A whole-cluster recovery drill must not count three
   guests on one Mac as independent disaster-recovery infrastructure.

These are acceptance requirements, not tests executed by this design step.

## Required acceptance evidence

1. New owned test volumes on dedicated disposable guest data disks; never reuse
   boot disks, old evidence or user data. Namespace/volume identities are checked
   before every destructive fault. Existing local volumes remain retained.
2. Continuous real PostgreSQL transactions on the Royak-mounted volume, with
   durable-commit settings and an independent acknowledgement oracle. A small
   checksummed fsync/rename workload separately tests filesystem semantics.
3. Hard-stop the active writer VM; restore service on another node with the
   same actual dataset. Check all acknowledged IDs/values and DB integrity.
   Separate failed/ambiguous transactions; no exactly-once claim.
4. Control-plane and data-plane partitions, asymmetric loss, former owner
   returning with stale storage, concurrent attach attempts and leader changes.
   Prove the old writer cannot write when a new writer owns the volume; absence
   of observed corruption alone is not proof of fencing.
5. Replica loss/resync, disk-full, explicit IO errors, interrupted recovery and
   corrupted/stale replica handling. No successful durable acknowledgement when
   the declared storage durability condition is not met.
6. Versioned PVC lifecycle, capacity/access-mode checks, namespace isolation,
   claim/volume delete and recreation, Retain/Delete behavior, node binding and
   orphan recovery. Never silently mount a fresh empty directory as the old PV.
7. Crash-consistent snapshot/restore plus a separately defined application-
   consistent backup path. Restore to new test volumes and verify bytes/DB
   integrity. A backup on the same Mac is not physical disaster recovery.
8. Resource/latency/resync measurements, raw replica/attachment/fencing events,
   exact versions/hashes, repeatable cleanup and longer endurance. Repeat on
   independent physical hosts before claiming physical-host HA.
9. Final owned-environment closeout is mandatory, not inferred from test exit0:
   inventory exact process starts/arguments, container IDs/labels, volumes,
   mounts, test interfaces/rules, sockets/listeners and the three owned VM UUIDs.
   Drain/stop only positively identified test resources, independently verify
   their absence and stop owned VMs after guest closeout. Retained UNKNOWN or
   ambiguous ownership requires its separate recovery decision; never prune
   shared Docker state or delete by a broad name prefix. Preserve current
   qualification dependencies and original failure evidence. Only after the
   final gates may a reviewed retention manifest separate reproducible caches
   from archived exact source/binaries/raw reports; verify archive restoration
   by content hashes without pretending restored files have old live inode
   identity. Keep secrets private and publish no raw credentials. Temporary
   artifacts, caches and test credentials must not enter the source commit.
   The [cleanup and retention plan](CLEANUP-AND-RETENTION-PLAN.md) records the
   categories and latest read-only inventory; it is not a deletion permit.

Network/quorum qualification is separate from storage/backup implementation and
**a green networking soak cannot close this stateful production gate**. AI
suggestions remain read-only and cannot authorize storage migration, recover a
stale replica, override quorum/fencing or delete data.
